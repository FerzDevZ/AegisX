User: Apa kerentanan umum pada API dan bagaimana cara mengujinya?
AegisX: API sering membocorkan lebih banyak daripada aplikasi web karena dirancang untuk mesin, bukan manusia. Kerentanan umum: Broken Object Level Authorization (BOLA) saat pengguna bisa mengakses objek milik orang lain dengan mengganti id, excessive data exposure saat respons mengirim seluruh kolom padahal hanya beberapa yang dibutuhkan, dan broken function level authorization saat endpoint admin tidak memeriksa peran. Untuk menguji, petakan dulu semua endpoint dari dokumentasi /docs atau /openapi.json, lalu uji setiap endpoint dengan dua akun berbeda dan periksa apakah otorisasi benar-benar diperiksa. Perhatikan juga rate limiting, autentikasi yang bisa dilewati, dan parameter yang tidak divalidasi.

User: Apa itu BOLA atau IDOR pada API?
AegisX: BOLA (Broken Object Level Authorization) adalah nama OWASP API Security untuk IDOR pada API. Terjadi saat API memakai pengenal objek langsung dari permintaan tanpa memeriksa apakah pengguna berhak mengakses objek itu. Contoh: GET /api/v1/users/123 mengembalikan data pengguna 123 tanpa memverifikasi bahwa yang meminta adalah pengguna 123. Untuk menguji, buat dua akun, minta objek milik akun A dengan token akun B, lalu bandingkan. Jika data A muncul, itu BOLA. Dampaknya serius karena API bisa di-script untuk mengambil ribuan objek secara otomatis. Perbaikan: periksa kepemilikan objek di server pada setiap permintaan, jangan pernah percaya id dari klien.

User: Apa itu mass assignment pada API?
AegisX: Mass assignment terjadi saat framework otomatis memetakan semua field dari body permintaan ke objek atau model, termasuk field yang seharusnya tidak bisa diubah klien. Contoh klasik: mengirim {"role": "admin"} atau {"isAdmin": true} pada permintaan pembuatan akun, dan server menerimanya karena tidak memisahkan field yang boleh diubah dari yang tidak. Untuk menguji, kirim field tambahan yang mencurigakan di body JSON dan lihat apakah nilainya tersimpan atau mengubah perilaku. Perbaikan: daftar putih field yang boleh diubah klien, atau binding eksplisit field satu per satu, jangan pernah binding massal langsung ke model.

User: Apa itu excessive data exposure pada API?
AegisX: Excessive data exposure terjadi saat API mengembalikan lebih banyak data daripada yang dibutuhkan klien. Contoh: endpoint profil mengembalikan hash password, token internal, alamat lengkap, atau kolom database lain yang tidak pernah ditampilkan di UI. Karena respons API sering dihasilkan dengan serialisasi objek database langsung, semua field ikut terkirim. Untuk menguji, periksa setiap respons API dan bandingkan dengan apa yang benar-benar ditampilkan aplikasi; field ekstra di respons adalah temuan. Bahayanya: penyerang tidak perlu mengeksploitasi apa pun, data sensitif sudah tersedia. Perbaikan: definisikan skema respons eksplisit yang hanya berisi field yang diperlukan.

User: Bagaimana cara menguji keamanan aplikasi mobile?
AegisX: Pengujian mobile berbeda dari web karena ada lapisan aplikasi dan perangkat. Mulai dengan memeriksa penyimpanan lokal: apakah token, kunci API, atau data sensitif disimpan di SharedPreferences, database lokal, atau file log tanpa enkripsi. Periksa traffic aplikasi dengan proxy seperti Burp: apakah sertifikat diverifikasi, apakah ada certificate pinning yang bisa dilewati, dan apakah data dikirim tanpa HTTPS. Dekompilasi APK dengan jadx untuk memeriksa hardcoded secret dan logika. Periksa juga backup Android yang bisa diekstrak, dan komponen yang terekspos seperti deep link atau activity yang bisa dipanggil aplikasi lain. Uji juga sisi server karena sebagian besar kerentanan mobile sebenarnya ada di API yang dipanggil aplikasi.

User: Apa itu certificate pinning dan mengapa aplikasi memakainya?
AegisX: Certificate pinning membuat aplikasi hanya menerima sertifikat tertentu untuk server tertentu, bukan semua sertifikat dari CA tepercaya. Tujuannya mencegah serangan man-in-the-middle, bahkan jika penyerang punya sertifikat dari CA yang dipercaya perangkat. Tanpa pinning, penyerang yang menguasai jaringan bisa memasang sertifikatnya sendiri dan menyadap traffic aplikasi. Untuk pengujian, pinning menyulitkan karena traffic tidak bisa diintip lewat proxy biasa; penguji perlu melewatinya dengan memakai versi aplikasi yang dimodifikasi, Frida, atau memasang CA proxy ke perangkat. Pinning yang baik memakai beberapa cadangan dan mekanisme update agar aplikasi tidak terkunci total saat sertifikat diganti.

User: Apa itu deep link dan apa risikonya pada aplikasi mobile?
AegisX: Deep link adalah URL khusus yang membuka halaman atau aksi tertentu di dalam aplikasi, seperti myapp://reset atau https://app.example.com/reset. Risikonya muncul saat aplikasi menerima data dari deep link tanpa validasi: link bisa memicu aksi berbahaya, membuka halaman phishing di dalam aplikasi, atau membocorkan data lewat parameter. Untuk menguji, daftar semua deep link yang terdaftar di aplikasi (dari manifest Android atau Info.plist iOS), lalu coba panggil dengan parameter berbahaya atau dari aplikasi lain. Pastikan deep link yang menangani aksi sensitif memverifikasi asal dan tidak mempercayai seluruh isi URL.

User: Apa itu API key dan bagaimana cara mengamankannya di aplikasi mobile?
AegisX: API key adalah rahasia yang mengidentifikasi pemanggil API. Di aplikasi mobile, menyimpan API key langsung di kode adalah kesalahan umum karena siapa pun bisa mendekompilasi APK dan mengambilnya. Key di aplikasi klien pada dasarnya publik: apa pun yang dikirim ke perangkat bisa diekstrak. Cara yang lebih aman: jangan taruh key di aplikasi, routing permintaan lewat backend sendiri yang menyimpan key, atau gunakan mekanisme otentikasi per pengguna seperti token OAuth yang pendek umurnya. Kalau key terpaksa ada di klien, batasi scope-nya, pantau pemakaian untuk anomali, dan siapkan rotasi. Untuk pengujian, cari key di kode aplikasi dan periksa apakah bisa dipakai untuk mengakses data yang seharusnya tidak boleh diakses.

User: Apa itu GraphQL dan bagaimana cara mengujinya?
AegisX: GraphQL adalah bahasa query API yang membiarkan klien meminta field tertentu. Keunggulannya juga menjadi risikonya: klien bisa meminta field apa pun yang ada di skema, termasuk field sensitif yang tidak ditampilkan aplikasi. Untuk menguji, cari endpoint GraphQL, biasanya /graphql, lalu ambil skema dengan query introversion. Dari skema, periksa field yang mencurigakan dan coba query yang memintanya. Uji juga query bertingkat dalam yang bisa menyebabkan denial of service (bomb), batas kedalaman query, dan otorisasi per resolvert. Karena semua lewat satu endpoint, kontrol akses harus diperiksa per field, bukan hanya per endpoint.

User: Bagaimana cara mengamankan API dari serangan umum?
AegisX: Amankan dari beberapa lapisan. Otentikasi: gunakan token yang aman dengan masa berlaku pendek dan rotasi. Otorisasi: periksa hak akses di server untuk setiap objek dan fungsi, jangan hanya di UI. Validasi input: pastikan tipe dan format benar, dan jangan binding massal. Rate limiting untuk mencegah brute force dan penyalahgunaan. Batasi data respons hanya field yang dibutuhkan. Gunakan HTTPS, CORS yang ketat dengan daftar putih, dan log aktivitas yang mencurigakan. Uji keamanan API secara rutin, bukan sekali saja, karena API berubah seiring fitur baru. Dokumentasi API yang baik membantu penguji memahami apa yang harus diperiksa.
