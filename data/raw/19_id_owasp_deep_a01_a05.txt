User: Bagaimana cara menguji broken access control (A01) secara praktis?
AegisX: Mulai dengan memetakan peran dan fungsinya: daftar endpoint yang hanya boleh diakses admin, dan mana yang untuk pengguna biasa. Buat dua akun berbeda lalu uji IDOR dengan mengganti nilai id, uid, atau nomor referensi di URL, body, dan header saat memakai sesi akun lain. Uji akses langsung ke endpoint admin tanpa login dengan mengubah metode HTTP: GET menjadi POST, atau menambah header X-Original-URL dan X-Rewrite-URL. Coba akses file yang seharusnya privat dengan mengubah ekstensi atau path. Periksa apakah kontrol akses ada di server atau hanya disembunyikan di menu klien, karena tombol yang disembunyikan tidak melindungi apa pun. Untuk memperbaiki, terapkan pemeriksaan otorisasi di server pada setiap permintaan, jangan hanya mengandalkan UI.

User: Bagaimana cara menguji dan memperbaiki cryptographic failure (A02)?
AegisX: Periksa semua data yang sensitif: kata sandi, nomor kartu, token, dan data pribadi. Uji apakah data dikirim lewat HTTP biasa, apakah respons mengungkap data sensitif, dan apakah data disimpan tanpa enkripsi. Periksa algoritma yang dipakai: jangan terima MD5, SHA1, atau DES untuk hash kata sandi; gunakan bcrypt, scrypt, atau Argon2. Periksa apakah padding oracle memungkinkan pembacaan data terenkripsi. Untuk kunci enkripsi, pastikan dikelola lewat sistem manajemen kunci dan dirotasi, bukan hardcoded di kode. Perbaikan utama: enkripsi data saat transit dengan TLS 1.2+, enkripsi data saat istirahat, dan jangan menyimpan data yang tidak perlu. Enkripsi tanpa melindungi kunci hanyalah teater keamanan.

User: Bagaimana cara menguji injection (A03) selain SQL injection?
AegisX: Injection tidak hanya SQL. Uji command injection dengan memasukkan perintah sistem lewat parameter yang diteruskan ke fungsi shell, misalnya parameter hostname yang dijalankan dengan ping. Uji LDAP injection, XPath injection, dan template injection dengan payload seperti {{7*7}} di aplikasi yang memakai mesin template. Untuk mendeteksi, amati respons yang berbeda, error yang bocor, dan waktu eksekusi. Cara paling efektif menemukan injection adalah fuzzing parameter dengan daftar payload lalu membandingkan respons. Perbaikan: jangan pernah membangun query atau perintah dengan menggabungkan string; pakai parameterized query, API yang aman, dan validasi input dengan daftar putih. Prinsip intinya: pisahkan data dari kode, dan perlakukan setiap input sebagai data yang tidak tepercaya.

User: Bagaimana cara menguji insecure design (A04)?
AegisX: Insecure design berbeda dari implementasi yang salah: ini cacat pada tahap desain. Untuk mengujinya, pelajari alur bisnis aplikasi: sistem poin, kupon, saldo, batas percobaan, dan proses verifikasi. Cari asumsi yang salah, misalnya mengira pengguna tidak akan mengubah harga di body permintaan, atau mengira batas unduhan hanya perlu disembunyikan di klien. Uji alur negatif: daftar ulang dengan email sama, gunakan kupon berkali-kali, ubah jumlah pada transaksi, lewati langkah verifikasi dengan memanggil endpoint berikutnya langsung. Kerentanan desain sulit diperbaiki dengan patch karena harus diubah sejak awal. Dokumentasikan setiap pelanggaran logika bisnis sebagai temuan dengan langkah reproduksi yang jelas.

User: Bagaimana cara menguji security misconfiguration (A05)?
AegisX: Misconfiguration adalah salah satu kerentanan paling umum dan paling mudah ditemukan. Periksa header HTTP respons: apakah Server dan X-Powered-By membocorkan versi, apakah header keamanan seperti Content-Security-Policy, X-Frame-Options, dan HSTS ada. Coba akses file sensitif: /robots.txt, /.git/config, /backup.zip, direktori dengan directory listing aktif, dan file konfigurasi yang tidak sengaja terpublikasi. Periksa akun default: coba admin/admin, root, dan kredensial bawaan perangkat lunak. Uji metode HTTP yang tidak perlu seperti PUT dan DELETE. Untuk memperbaiki: matikan directory listing, hapus file contoh dan cadangan, set header keamanan, ganti semua kredensial default, dan otomatiskan proses konfigurasi dengan infrastruktur sebagai kode agar tidak ada server yang melenceng dari standar.

User: Bagaimana cara mendeteksi kerentanan pada komponen yang sudah usang (A06)?
AegisX: Komponen yang usang berarti perangkat lunak, pustaka, dan dependensi yang dipakai aplikasi mengandung kerentanan yang sudah diketahui publik. Cara mendeteksi: buat inventaris semua komponen dan versinya dari file manifest seperti package.json, requirements.txt, pom.xml, dan Gemfile.lock. Cocokkan dengan database kerentanan memakai alat seperti OWASP Dependency-Check, Snyk, atau GitHub Dependabot. Periksa juga versi server web, framework, dan CMS dari banner dan fingerprint. Risiko paling nyata adalah komponen dengan CVE yang dieksploitasi aktif. Perbaikan: perbarui secara rutin, otomatiskan pemindaian dependensi dalam CI, hapus komponen yang tidak terpakai, dan berlangganan feed keamanan vendor. Kerentanan yang sudah punya patch selama berbulan-bulan adalah kegagalan proses, bukan nasib.

User: Bagaimana cara menguji identification and authentication failures (A07)?
AegisX: Fokus pada mekanisme yang membuktikan identitas pengguna. Uji kebijakan kata sandi: apakah kata sandi lemah diterima, apakah ada daftar kata sandi umum yang diblokir. Uji brute force: apakah ada pembatasan percobaan login dan akun terkunci setelah beberapa kali gagal. Periksa alur lupa kata sandi: apakah token reset bisa ditebak, apakah tautan reset tidak kedaluwarsa, dan apakah token dikirim lewat saluran yang aman. Periksa sesi: apakah session ID bisa ditebak, apakah tidak berubah setelah login, dan apakah logout benar-benar menghancurkan sesi. Uji autentikasi multifaktor: apakah bisa dilewati, apakah kode MFA bisa ditebak atau dipakai ulang. Perbaikan: aktifkan MFA, batasi percobaan login, gunakan mekanisme anti-otomatisasi, dan rotasi session ID setelah autentikasi.

User: Bagaimana cara menguji software and data integrity failures (A08)?
AegisX: Kerentanan ini terjadi saat kode atau data tidak diverifikasi integritasnya. Uji apakah aplikasi memuat kode dari sumber yang tidak tepercaya tanpa verifikasi, misalnya plugin, pembaruan, atau pustaka dari CDN tanpa subresource integrity. Periksa deserialisasi data yang tidak tepercaya: coba payload deserialization untuk memicu eksekusi kode atau perilaku berbahaya. Uji pipeline CI/CD: apakah perubahan kode bisa disuntikkan tanpa review, apakah dependensi bisa diganti lewat serangan supply chain seperti typosquatting. Periksa pembaruan otomatis: apakah pembaruan diverifikasi tanda tangannya. Perbaikan: gunakan tanda tangan digital dan checksum untuk semua artefak, terapkan subresource integrity pada aset pihak ketiga, validasi struktur data sebelum deserialisasi, dan lindungi pipeline dengan review dan kontrol akses yang ketat.

User: Bagaimana cara menguji security logging and monitoring failures (A09)?
AegisX: Kerentanan ini tidak terlihat oleh pengguna tetapi menentukan apakah serangan bisa dideteksi. Uji apakah peristiwa penting dicatat: login gagal dan sukses, perubahan hak akses, akses data sensitif, penghapusan data, dan kegagalan validasi. Periksa apakah log menyertakan konteks yang cukup: waktu, alamat IP, pengguna, dan aksi yang dilakukan, tanpa mencatat data sensitif seperti kata sandi. Uji apakah log bisa dipalsukan atau dihapus oleh penyerang yang sudah masuk. Periksa apakah ada alert yang benar-benar memicu respons saat pola mencurigakan muncul. Perbaikan: catat semua peristiwa keamanan penting, lindungi log agar tidak bisa diubah, kirim ke sistem terpusat seperti SIEM, dan buat aturan deteksi serta prosedur respons. Jika tidak ada log, serangan berjalan tanpa jejak dan kegagalan tidak pernah terpelajari.
