Web application testing is the core of modern penetration testing because most businesses expose their value through web applications. The Open Web Application Security Project publishes the OWASP Top 10, a list of the most critical web application security risks. The list is updated every few years and reflects the most common and dangerous vulnerabilities found in real applications.

Injection flaws occur when untrusted data is sent to an interpreter as part of a command or query. The most common injection flaw is SQL injection, where user input is concatenated into a SQL query. If an application builds a query like SELECT FROM users WHERE username = '$input', an attacker can submit a username of ' OR '1'='1 to bypass authentication or extract the entire database. The fix is parameterized queries, which separate the SQL structure from the data. Never concatenate user input into SQL, operating system commands, or LDAP queries.

Broken authentication covers flaws in login and session management. Attackers can compromise passwords, session tokens, or exploit implementation flaws to impersonate other users. Common issues include allowing weak passwords, failing to lock accounts after repeated failures, exposing session IDs in URLs, and not expiring sessions after logout. Multi-factor authentication mitigates many authentication attacks. Session tokens must be random, transmitted only over HTTPS, and stored in secure cookies.

Sensitive data exposure happens when applications fail to protect important data like credit card numbers, credentials, or personal information. The main defenses are encryption in transit with TLS and encryption at rest. Never store passwords in plain text; store a salted hash using a strong algorithm like bcrypt, scrypt, or Argon2. Never log sensitive data. Use the principle of least privilege so that only the parts of the system that need data can access it.

XML External Entity attacks, or XXE, occur when an application parses XML input that contains references to external entities. An attacker can define an entity that reads a local file, so parsing the XML returns the contents of that file to the attacker. XXE can read /etc/passwd, internal files, and can sometimes access internal network services. The fix is to disable external entity processing in the XML parser. Modern parsers disable XXE by default, but legacy code often enables it for convenience.

Broken access control means users can access functionality or data they should not be able to reach. Horizontal privilege escalation lets a user access another user's data, like changing the account ID in a URL to view another user's profile. Vertical privilege escalation lets a regular user access admin functionality. Access control checks must run on the server for every request. Never rely on hiding buttons or menus in the client; an attacker can call the endpoint directly. Check object-level access on every request that uses an object identifier.

Security misconfiguration is the most common issue in the OWASP Top 10. Examples include running software with default credentials, leaving debug mode enabled in production, exposing detailed error messages, allowing directory listing, and using outdated software with known vulnerabilities. The fixes are simple: remove default accounts, disable debug modes, return generic error messages, disable directory listing, and patch software regularly. A hardening checklist applied to every deployment prevents most misconfiguration findings.

Cross-Site Scripting, or XSS, lets an attacker inject client-side scripts into web pages viewed by other users. Reflected XSS occurs when the input is immediately reflected in the response without sanitization, like a search page that echoes the query. Stored XSS occurs when the payload is saved on the server and displayed to everyone who views the page, like a comment field. DOM-based XSS happens entirely in the browser when JavaScript reads untrusted input from the URL and writes it to the page. The primary defense is context-aware output encoding: encode HTML, attributes, JavaScript, and URLs differently. Content Security Policy headers add a second layer of defense by restricting which scripts can execute.

Insecure deserialization occurs when untrusted data is deserialized by the application. Attackers can manipulate the serialized object to execute arbitrary code, inject objects, or tamper with application logic. Java, PHP, Python, and .NET all have deserialization vulnerabilities in their libraries. The safest approach is to avoid deserializing untrusted data entirely. If you must, use allow-lists of permitted classes, sign the serialized data, and run deserialization in a sandbox.

Using components with known vulnerabilities is a direct consequence of poor patch management. Applications are built from many libraries and frameworks, and each one can have published vulnerabilities. Tools like OWASP Dependency-Check and Snyk scan dependencies and report known vulnerabilities. The National Vulnerability Database assigns CVE identifiers to every significant vulnerability. A CVE identifier has the format CVE-YEAR-NUMBER, like CVE-2021-44228 which is the Log4Shell vulnerability in the Java logging library Log4j. Log4Shell is a critical remote code execution flaw that was exploited within days of disclosure. Keeping dependencies current and scanning them regularly is the only reliable defense.

Insufficient logging and monitoring lets attacks go unnoticed. If an application does not log authentication failures, suspicious input, and privilege changes, defenders cannot detect a breach until it is too late. Logs must include timestamps, user identifiers, source IP addresses, and the outcome of each action. Centralize logs and alert on anomalies. Detection and response capability is as important as prevention. A vulnerability that is detected within minutes causes far less damage than one discovered months later.

Server-Side Request Forgery, or SSRF, happens when an attacker can make the server send requests to arbitrary destinations. A URL parameter that the server fetches can be pointed at internal services like 169.254.169.254, the cloud metadata endpoint that contains credentials. SSRF is one of the most dangerous web vulnerabilities because it bridges the network boundary. Validate and allow-list the destinations the server can request, block private IP ranges, and never return the raw response body to the client.

The best way to learn web application security is to practice on intentionally vulnerable applications. DVWA, WebGoat, Juice Shop, and PortSwigger's Web Security Academy all provide safe environments for practicing attacks. Never practice against real systems without permission. These lab environments let you make mistakes safely and understand both the attack and the defense from the inside.
