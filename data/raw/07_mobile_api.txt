Mobile application security and API security are two of the fastest-growing areas of penetration testing. Modern applications are built as thin clients talking to powerful backend APIs. The mobile app is often the least secure component, because developers focus security effort on the web application while forgetting that the mobile client exposes the same API.

Mobile applications inherit the security problems of the APIs they call, plus new problems of their own. The first question in any mobile test is whether the app correctly stores sensitive data. Never store secrets in plain text on the device. API keys, tokens, and user data belong in the platform secure storage: the Android Keystore or iOS Keychain. Hardcoding API keys inside the app binary is a common flaw: attackers can extract strings from the APK or IPA and reuse the keys to access backend services directly.

Interception is the core technique for mobile testing. Set up a proxy like Burp Suite and configure the device to route traffic through it. Install the proxy certificate on the device so HTTPS traffic can be decrypted. Many apps implement certificate pinning, which refuses to trust any certificate except a specific one. Pinning defends against interception but can be bypassed with tools like Frida, which hook into the application at runtime and disable the pinning check. If an app trusts all certificates or disables TLS validation, that is a finding in itself.

The Android application package, or APK, can be analyzed statically. Tools like jadx decompile the APK into readable Java or Kotlin source code. Apktool decodes resources and smali code. Static analysis reveals hardcoded secrets, insecure API endpoints, weak cryptography, and logic flaws. The manifest file declares permissions and components; excessive permissions are a finding because they expand the damage a compromised app can do. The iOS equivalent is the IPA file, analyzed with tools that decrypt and inspect the Mach-O binary and its resources.

Exporting components is an Android-specific weakness. Activities, services, and content providers declared with the exported attribute can be invoked by other applications. An exported activity might bypass the login screen when launched directly with an intent. An exported content provider might allow other apps to read or modify its data. Test every exported component for unauthorized access by trying to invoke it from another application context.

API security starts with authentication and authorization. The most common API flaw is broken object-level authorization, abbreviated BOLA and also known as IDOR. When an API endpoint takes an object identifier like a user ID, order ID, or document ID, it must verify the caller owns that object. Testing is simple: authenticate as user A, request user B's resource by changing the identifier, and observe whether the API returns it. Automated tools like the Autorize extension automate this check across every endpoint.

API enumeration reveals the attack surface. OpenAPI specifications, often exposed at paths like /swagger, /api-docs, or /openapi.json, document every endpoint and parameter. Even without documentation, endpoint patterns reveal themselves: /api/v1/users, /api/v1/users/123, /api/v1/users/123/orders. Versioned APIs may leave old versions running with weaker security. Testing both v1 and v2 of an endpoint can uncover authorization checks added only to the newest version.

Rate limiting protects APIs from abuse. Endpoints that send email, reset passwords, or verify codes must limit how often they can be called. Without rate limiting, attackers brute force login credentials, enumerate user accounts through differing responses, or flood email endpoints. Test rate limits by sending rapid repeated requests and checking whether the API responds with a limit error or just keeps processing. The absence of rate limiting combined with an account enumeration vector is a serious finding.

JWT tokens are the standard for API authentication. A JSON Web Token has three parts: a header, a payload, and a signature. Common JWT flaws include accepting the none algorithm, not verifying the signature, using weak signing keys that can be brute forced, and placing sensitive data in the unsigned payload. The jwt.io debugger decodes tokens for inspection. If a token's payload contains a role or user identifier that the API trusts without verifying the signature, an attacker can forge tokens simply by editing the payload.

Business logic in APIs mirrors business logic in web applications. Discount codes, loyalty points, referral bonuses, and balances are all logic targets. Try applying operations in unexpected orders, reusing one-time codes, or processing the same transaction twice. APIs that expose balance transfers or reward systems are prime race condition targets. Every state-changing API call should be tested for whether it validates the business rule server-side rather than trusting the client.

Mobile and API findings usually have high impact because they affect every user of the application. A broken object-level authorization flaw in a banking API exposes every customer's transactions. A hardcoded key in a mobile app grants access to the entire backend. Report these findings with clear reproduction steps: the exact request, the authenticated session used, and the response received. Screenshots of the request in Burp Suite make the finding undeniable to triagers.
